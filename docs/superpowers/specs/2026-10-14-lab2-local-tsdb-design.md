## 2. Что в скоупе и что нет

В скоупе:

- Публичный API: `DefaultTSDB`, `HeadAppender`, `DefaultQuerier`.
- Единый внутренний интерфейс `SeriesSource` для Head и блока.
- Ленивый k-way merge источников по `Labels`.
- Формат блока на диске: `meta.json`, `chunks`, `index`, `tombstones`.
- `BlockWriter` с атомарной публикацией через `rename`.
- `FileStorage`: скан каталога при старте, чистка `.tmp`.
- Флаш по ручному вызову и по порогу времени данных.
- Удаление через tombstones, включая уже сброшенные блоки.

Вне скоупа, сознательно:

- WAL и crash-recovery. Исключены в `docs/specs.md` для первой итерации.
  WAL придёт в лабе 4 вместе с репликацией, его формат определят требования
  подписки реплик. Писать его сейчас значит переделывать потом.
- Компакция и бамп блоков.
- Сжатие: XOR, дельта-кодирование, LZ4.
- mmap.
- Матчеры кроме `=`.
- PromQL и любые операторы над результатом.
- REST и gRPC. Это лаба 3.

## 3. Архитектура

### 3.1 Единый интерфейс источника

Вся симметрия Head и диска держится на одном внутреннем интерфейсе:

```kotlin
internal interface SeriesSource : AutoCloseable {
    val range: TimeRange
    /** Серии отсортированы по Labels. Сэмплы ленивые. */
    fun select(range: TimeRange, matchers: List<Matcher>): SeriesSet
}
```

Реализуют `MemoryHead` и `DiskBlock`. Больше ни один компонент не знает,
откуда пришли данные.

### 3.2 Слой слияния

- `MergeSeriesSet(sources: List<SeriesSet>)`: k-way merge по `Labels` через
  `PriorityQueue` с компаратором по текущим лейблам каждого источника.
- `MergeSeriesIterator(iters: List<SeriesIterator>)`: при совпадении `Labels`
  сливает сэмплы по таймстемпу.

Приоритет при равном таймстемпе из разных источников: **Head выигрывает**,
он свежее блока. Без этого правила тесты недетерминированы.

### 3.3 Что ленивое, а что нет

Ленивые здесь сэмплы, не список серий.

Пересечение postings материализуется: `PostingList.query` возвращает
`List<SeriesRef>`. Список подходящих серий материализуется в каждом источнике
и сортируется по `Labels`. Серий мало, сэмплов много, выигрыш там, где нужен.
Prometheus поступает так же.

### 3.4 SeriesRef локален для источника

`SeriesRef` остаётся `value class(Long)` и **валиден только внутри своего
источника**:

- в Head это id из `LongSequence`;
- в блоке это оффсет записи в секции `Series`.

Между источниками они не сравниваются никогда, потому что merge работает по
`Labels`. Поэтому двух типов не нужно.

`internal` с `SeriesRef` снимается, иначе проект не компилируется (раздел 9).

## 4. Формат блока на диске

Структура из `docs/structure-and-usecases.md` сохранена целиком. Упрощено
только кодирование.

```
<data-dir>/
├── 01K7XJ8M.../            ULID, лексикографически = хронологически
│   ├── chunks/000001
│   ├── index
│   ├── meta.json
│   └── tombstones
└── 01K7XJ9P....tmp/        недописанный блок, чистится при старте
```

### 4.1 Отклонения от спеки форматов

| В спеке | Здесь | Обоснование |
|---|---|---|
| `uvarint`, `varint` | `int32`, `int64`, big-endian | нет кодировщика varint и его багов |
| дельта-кодирование чанков | абсолютные `mint`, `maxt`, оффсет | дельты экономят место, структуру не меняют |
| `seriesRef * 16`, align 16 байт | `seriesRef` = прямой оффсет в `index` | align нужен, чтобы ref влез в 32 бита |
| CRC32 «можно выкинуть» | оставлен | ловит битый файл, стоит 3 строки |

Порядок файлов и секций не меняется. Позже подменяется только кодировщик,
читатель уровнем выше не трогается.

### 4.2 index

```
magic 0xBAAAD700 : int32
version 1        : int8

Symbol Table    : len:int32, count:int32, count × [len:int32, utf8], crc32:int32
Series          : per series → len:int32,
                    labelsCount:int32, labelsCount × [nameRef:int32, valueRef:int32],
                    chunksCount:int32, chunksCount × [mint:int64, maxt:int64,
                                                      chunkFile:int32, chunkOffset:int64],
                    crc32:int32
Postings 1..N   : len:int32, count:int32, count × ref:int64, crc32:int32
Postings Offset : len:int32, count:int32,
                    count × [nameLen:int32, name, valueLen:int32, value, offset:int64],
                    crc32:int32
TOC             : 36 байт, в САМОМ КОНЦЕ файла
```

TOC лежит в конце, потому что писатель узнаёт оффсеты только после записи
секций. Размер фиксированный, читатель делает один `seek(fileLength - 36)`.

`Series` отсортированы по `Labels`. Это даёт блоку сортированный вывод
бесплатно: записи читаются по порядку.

### 4.3 Запрос «все серии»

Пустой список матчеров возвращает все серии. Для этого в Postings Offset Table
резервируется запись с парой `("", "")`, содержащая список всех серий
(в Prometheus это `allPostings`). Иначе пришлось бы сканировать `Series`.

Тот же путь появляется в `PostingList` в Head. Это чинит баг B из раздела 9.

### 4.4 chunks

```
magic 0x43484E4B : int32
version 1        : int8
padding          : 3 байта
per chunk        : len:int32, encoding:int8,
                   data = [count:int32, count × (ts:int64, value:float64)],
                   crc32:int32
```

`encoding`: 1 = RAW. XOR не реализуется.

`len` это длина **только** секции `data`, без байта `encoding` и без `crc32`.
CRC считается по `encoding` плюс `data`. Читатель, зная `len`, может
перепрыгнуть чанк не разбирая его.

В `tombstones` и в секциях `index` добавлено поле `count`, которого нет в
спеке форматов. Без него читателю пришлось бы выводить число записей из
длины секции, что ломается при изменении размера записи.

### 4.5 tombstones, единственный мутабельный файл

```
magic 0x0130BA30 : int32
version 1        : int8
count            : int32
count × [seriesRef:int64, mint:int64, maxt:int64]
crc32            : int32
```

`delete()` по сброшенным данным дописывает маркеры сюда. Файл маленький,
перезаписывается целиком: `tombstones.tmp`, `fsync`, `rename`. Остальные файлы
блока иммутабельны навсегда.

### 4.6 meta.json

Читаемый JSON через `kotlinx.serialization`. Поля по образцу из спеки: `ulid`,
`minTime`, `maxTime`, `stats.numSamples`, `stats.numSeries`, `stats.numChunks`,
`compaction.level`, `version`.

Выбор библиотеки осознанный: ручной парсер JSON это лишние баги, а читаемость
нужна для демо (`cat meta.json` на защите).

### 4.7 Атомарность и старт

- `BlockWriter` пишет в `<ulid>.tmp/`, делает `fsync`, затем `rename` в
  `<ulid>/`. Rename атомарен в пределах файловой системы.
- `FileStorage.open(dir)`: удаляет все `*.tmp`, читает `meta.json` из
  остальных папок, открывает `DiskBlock` на каждую.

## 5. Публичный API

### 5.1 Флаш: Head не знает про диск

Отклонение сразу от двух мест. В коде PR #7 метод называется
`trim(minTime: TimeRange): Block` (имя параметра `minTime`, а тип `TimeRange`,
возврат не nullable). В `pochti_ceasar/defense.md` заявлено
`truncate(minTime: Long): Block?`. Ни то, ни другое не подходит.

Метод переименовывается в `truncate(upTo: Long): HeadSnapshot?`. Это правка
интерфейса лабы 1, она необходима архитектурно.

Причина: `Block` это артефакт на диске. Чтобы Head его вернул, ему нужны папка,
ULID-генератор и писатель. Знание про диск уезжает внутрь in-memory компонента,
что ломает принцип «Head не знает про Storage», заявленный там же.

```kotlin
interface Head : SeriesSource {
    fun append(labels: Labels, timestamp: Long, value: Double)
    fun delete(range: TimeRange, matchers: List<Matcher>)
    /** Отрезает всё строго меньше upTo. null, если отрезать нечего. */
    fun truncate(upTo: Long): HeadSnapshot?
}

interface HeadSnapshot {
    val range: TimeRange
    val numSeries: Int
    val numSamples: Long
    fun series(): Iterator<SnapshotSeries>   // в порядке Labels
    fun tombstones(): List<Tombstone>
}
```

Путь флаша:

```
DefaultTSDB.flush()
  1. snapshot = head.truncate(upTo)              null → выход
  2. block    = BlockWriter(dir).write(snapshot) .tmp → fsync → rename
  3. storage.add(block)
```

Значение `upTo` зависит от того, кто позвал:

| Вызов | `upTo` | Что происходит |
|---|---|---|
| `TSDB.flush()` вручную | `Long.MAX_VALUE` | Head флашится целиком, становится пустым |
| `close()` | `Long.MAX_VALUE` | то же, durability при штатном завершении |
| автофлаш по порогу | `head.range.minTime + headWindow` | отрезается только устаревшее, свежее остаётся в Head |

`truncate` возвращает `null`, если под `upTo` не попало ни одного сэмпла.
Тогда блок не создаётся и пустая папка на диске не появляется.

Head отдаёт данные, `BlockWriter` пишет, `Storage` регистрирует. Tombstones из
Head переезжают в файл блока, иначе удаления теряются при флаше.

Цена: `truncate` идёт под `writeLock` Head, записи на это время блокируются.
Для MVP приемлемо, это известное упрощение.

### 5.2 Триггер флаша по времени данных

```kotlin
data class TSDBConfig(
    val headWindow: Long = 2 * 60 * 60 * 1000,   // 2 часа, как в Prometheus
    val stripeSize: Int = 16,                     // вместо магического 14
)
```

`commit()` смотрит на `head.range`. Если диапазон по **таймстемпам сэмплов**
шире `headWindow`, происходит флаш. Не по `System.currentTimeMillis()`.

Это принципиально для тестов: сэмплы с `t=0` и `t=3h` дают флаш детерминированно,
без `Thread.sleep`.

`fun flush()` добавляется в интерфейс `TSDB`. Нужен тестам и демо.

### 5.3 Appender

```kotlin
internal class HeadAppender(private val head: Head) : Appender {
    private val pending = ArrayList<Pending>()
    override fun add(labels: Labels, timestamp: Long, value: Double)  // в буфер
    override fun commit()    // применяет всё, чистит буфер, при необходимости флашит
    override fun rollback()  // чистит буфер
    override fun close()     // = rollback, если commit не вызывали
}
```

`add()` валидирует до буфера: лейблы непустые, `__name__` присутствует.
Исключение на `add()`, а не на `commit()`, чтобы ошибка была ближе к причине.

### 5.4 Семантика записи

| Случай | Поведение | Обоснование |
|---|---|---|
| дубликат пары (серия, timestamp) | последний выигрывает, перезапись | запись идемпотентна: ретрай HTTP в лабе 3 и переигрывание на реплике в лабе 4 не ломают данные |
| out-of-order сэмпл | принимается | `MemorySeries` уже умеет: отдельный сортированный список плюс merge на чтении |

Оба решения расходятся с `defense.md`, где заявлено «out-of-order отвергаются
при commit()». Документ надо поправить.

Перезапись требует правки `MemorySeries`: в in-order пути при `ts == latestTimestamp`
заменяется последнее значение, в out-of-order пути точное попадание
`binarySearch` заменяет элемент вместо вставки.

### 5.5 Querier и границы снэпшота

```kotlin
internal class DefaultQuerier(
    override val range: TimeRange,
    private val sources: List<SeriesSource>,
) : Querier
```

На `querier(range)` фиксируется список источников: Head плюс блоки,
пересекающиеся с `range`. `Storage` держит `@Volatile List<Block>`, querier
копирует ссылку. Компакции в лабе 2 нет, блоки не удаляются, use-after-free
невозможен.

Честное ограничение: Head продолжает мутировать под открытым querier. Полного
снэпшота нет, он требует MVCC или копии данных. Для блоков снэпшот настоящий,
для Head нет. Формулировку «консистентный снэпшот» в `defense.md` надо уточнить.

### 5.6 Durability

`DefaultTSDB.close()` флашит Head. Без WAL это единственный способ не потерять
свежие данные при штатном завершении.

Что работает: штатный `close`, рестарт, чтение блоков с диска.
Что не работает: `kill -9`, несброшенный Head теряется.

«Чтение при старте» и «crash-recovery» это разные вещи. У нас есть первое,
второго нет. На защите формулировать точно.

## 6. Тесты

### Уровень 1. Round-trip кодирования

`ChunkWriter` → `ChunkReader`, `IndexWriter` → `IndexReader`, tombstones,
`meta.json`. Ловит баги формата без участия Head и БД.

### Уровень 2. Head

append, query, delete, out-of-order, перезапись дубликата, сортированный вывод.
Закрывает пять багов из раздела 9.

### Уровень 3. Merge на фейковых источниках

1. Разные `Labels` в разных источниках, порядок вывода по лейблам.
2. Одинаковые `Labels` в Head и блоке, сэмплы сливаются по таймстемпу.
3. Одинаковый таймстемп в обоих, Head выигрывает.
4. Пустой источник в середине списка.
5. Три источника с перекрывающимися диапазонами.
6. Источник вне `range` не опрашивается вообще.
7. Все источники пустые, `next()` сразу `false`.

Уровень на фейках снимает зависимость самого рискового куска (merge) от самого
объёмного (формат блока).

### Уровень 4. End-to-end

1. append → query без флаша.
2. append → flush → query.
3. append → flush → append → query, merge Head и блока.
4. flush → close → reopen → query, данные переживают рестарт.
5. два флаша, два блока, query покрывает оба.
6. query по диапазону, попадающему только в один блок из двух.
7. query с пустым списком матчеров возвращает все серии.
8. `rollback` не применяет батч.
9. `close()` флашит Head: после `close` и повторного открытия данные на месте.
10. Данные, добавленные через `add()` без `commit()`, не попадают ни в Head,
    ни в блок после `flush()`.
11. Автофлаш по порогу: сэмплы с `t=0` и `t=3h` при `headWindow=2h` дают блок,
    свежее остаётся в Head.

### Уровень 5. Мусор и порча

1. Папка `.tmp` после «падения» удаляется при открытии.
2. Битый CRC в `chunks` даёт понятную ошибку, не молчаливый мусор.
3. `index` короче TOC даёт понятную ошибку.
4. Папка блока без `meta.json`.
5. Неизвестная `version` в magic.

### Уровень 6. Concurrency smoke

1. N потоков пишут в одну серию, итоговое число сэмплов сходится.
2. N потоков пишут в разные серии, все серии видны.
3. Писатели плюс читатель, читатель не падает.
4. Флаш параллельно с записью, данные не теряются.

## 7. Демонстрация работоспособности

Два артефакта.

**`./gradlew test`**: весь набор зелёный.

**`./gradlew run`**: сценарий в `Main.kt`, печатает каждый шаг.

```
1. Создаю БД в ./demo-data
2. Пишу 3 серии через Appender, commit
3. Запрос __name__="cpu"            → серии и сэмплы
4. Запрос __name__="cpu", host="a"  → пересечение postings
5. delete [t2, t3]                  → повторный запрос, видна дыра
6. flush()                          → дерево ./demo-data
7. Запрос снова                     → те же данные, помечен источник: HEAD или BLOCK
8. close(), открываю заново         → запрос, данные на месте
9. Out-of-order вставка и дубликат  → видна перезапись
```

Шаг 7 ключевой: пометка источника в выводе это единственный наглядный способ
доказать, что merge Head и блока работает, а не что данные лежат в памяти.

Вживую руками:

```bash
cat demo-data/01K7.../meta.json     # метаданные блока
xxd -l 16 demo-data/01K7.../index   # magic 0xBAAAD700 видно глазами
ls demo-data/                       # блоки есть, .tmp не осталось
```

Этим закрываются фичи, заявленные в `defense.md`: батчевая запись, чтение по
диапазону с фильтром, удаление через tombstones, иммутабельные блоки, postings,
symbol table, флаш.

## 9. Состояние PR #7 на входе

Ревью от 2026-10-14. Проверено сборкой и прогоном тестов.

### Блокеры

1. **Не компилируется**, 8 ошибок. `SeriesRef` сделан `internal`, его используют
   публичные `Postings`, `IndexReader`, `IndexWriter`, `storage/Tombstones`.
2. **Публичного API нет.** В `DefaultTSDB` все четыре метода это `TODO()`.
   `HeadManager` пустой класс.
3. **Флаша нет.** `MemoryHead.trim()` и `MemoryHead.range` это `TODO`.
4. **Тестов нет** на 830 строк новой логики.

### Воспроизведённые баги

| | Сценарий | Результат |
|---|---|---|
| B | `query(range, emptyList())` | `IndexOutOfBoundsException: Index 0 out of bounds for length 0` |
| C | `Series.iterator()` дважды | `first=[Sample(10, 1.0)]`, `second=[]` |
| D | два сэмпла с `t=10` | вернулись оба |
| E | `head.range` | `NotImplementedError` |
| F | `append()` после `close()` | данные потеряны молча, без исключения |

Причины:

- B: `PostingList.query` при пустых матчерах не заходит в цикл, затем
  `series[shortestListIndex]` падает на пустом списке.
- C: `LabelsSeries.iterator()` возвращает один и тот же инстанс.
- D: условие `timestamp >= latestTimestamp` в `MemorySeries.append`.
- F: `if (isClosed) { return }` без сигнала вызывающему.

### Что работает

Ядро живое: happy path, `delete` через tombstones, out-of-order вставка,
пересечение postings, striped-локи, merge in-order с out-of-order.

### Помельче

- `MemoryChunk.append` берёт id из `LongSequence` на каждый сэмпл, а не на новую
  серию. Инфлирует пространство `SeriesRef`.
- `Stripe.appendSeriesOrGet` пишет в `labelHashMap` и `refMap` под разными
  локами, неатомарно. Между ними запрос по ref серию не найдёт.
- `.idea/*` файлы в PR.
- `Stripe(14)`: не степень двойки, магическое число.
- `MemoryChunk.query`: `val series = series[ref]` затеняет внешнюю переменную.

## 10. Статус defense.md и правки документации

`pochti_ceasar/defense.md` писался под защиту лабы 1, где фиксировались только
интерфейсы. Это черновик контракта, а не замороженная спецификация. Свойства
уточняются по мере реализации, поэтому расхождения ниже ожидаемы и не являются
отступлением от плана. Документ обновляется к защите лабы 2.

Что изменилось относительно него:

| В defense.md | Здесь | Почему |
|---|---|---|
| out-of-order отвергаются при `commit()` | принимаются | `MemorySeries` уже умеет, выбрасывать работающее незачем |
| про дубликат таймстемпа не сказано | последний выигрывает | идемпотентность записи для лаб 3 и 4 |
| `truncate(minTime: Long): Block?` | `truncate(upTo: Long): HeadSnapshot?` | Head не должен знать про диск |
| «консистентный снэпшот блоков» | верно для блоков, не для Head | полный снэпшот требует MVCC |
| «автоматический флаш по времени и размеру» | только по времени данных | порог по размеру не нужен для MVP |
| crash-recovery в списке фич | отсутствует | нет WAL, см. раздел 2 |

`README.md`: статус лабы 2, команды запуска демо.
